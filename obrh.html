01 / The bigger picture

What integration work solves

The integration problem

Applications use different formats and depend on different backends. An integration hub gives them a controlled place to translate messages and select a destination.

The product idea

OBRH stands for Oracle Banking Routing Hub. Oracle describes consumers, providers, transformation, routing, and chaining as parts of its integration model.

The engineering lesson

Keep the caller's contract, routing decision, message translation, transport client, and operational signals understandable as separate responsibilities.

My resume records Java and Spring Boot development, Apache Camel integration, caching and query optimization, and production delivery work. These notes explain those areas. A platform capability or library feature is not automatically a feature I personally built.

Public learning notes with fictional services and original explanations. Source code, internal configuration, client data, and deployment details are excluded.

02 / Follow a request

One request. Several responsibilities.

A fictional application looks up an order through Service A or Service B. Select a step to see what it does. This is a teaching model, not a client architecture diagram.

Step 1 / 6

Receive

A fictional order application sends a lookup request. The boundary checks required fields and creates a correlation identifier, a label used to follow the same request through processing.

What comes out
A valid request and traceable context.
Think about
Are the inputs valid before any external call?
Step 2 / 6

Resolve

The routing layer looks up approved configuration. A cache may speed up reusable configuration reads. This example chooses Service A or Service B using a documented rule.

What comes out
A selected route and the settings it needs.
Think about
Can a configuration change make a cached decision stale?
Step 3 / 6

Transform

The message is converted to the format expected by the selected service. A transformation changes representation while preserving the intended meaning.

What comes out
A provider-ready message.
Think about
Are missing values, numeric precision, dates, and namespaces handled?
Step 4 / 6

Call

An adapter calls an HTTP API or a SOAP service. SOAP commonly runs over HTTP. Reusing clients may reduce setup work. A timeout bounds waiting; it does not prove the remote operation was cancelled.

What comes out
A response, a known failure, or an uncertain timeout.
Think about
Would a repeat be safe if the first call already succeeded?
Step 5 / 6

Normalize

The response is converted into the caller-facing contract. A transport error, a validation error, and a business rejection are different outcomes.

What comes out
A caller-friendly result with a suitable status.
Think about
Can the caller distinguish rejection from unavailability?
Step 6 / 6

Observe

Duration, outcome, and correlation information support monitoring. Audit work has its own delivery policy. Private payload values should be masked or omitted.

What comes out
An operational trail with only necessary data.
Think about
Can an engineer find the failing step without reading customer data?

01ArchitectureIntegration hub and responsibilitiesKeep the caller-facing contract separate from provider details.+

An integration service connects applications that may use different protocols, field names, and availability rules. The useful boundary is the contract: what the caller asks for and what it receives.

A routing decision selects a provider. A transformation translates the message. A transport client makes the call. Separating these concerns makes changes easier to reason about.

How to reason about it

  1. Identify the caller-facing contract.
  2. Choose a provider using an approved rule.
  3. Translate, call, and map the result back.
Fictional example

A fictional order application keeps one lookup contract while two providers use different field names.

Remember: The integration hub is not automatically the owner of the business transaction. Identify which system owns the result.

02ArchitectureConfiguration lifecycle and runtime executionSaving a rule and using it are different activities.+

Configuration management defines mappings and routing rules. Runtime execution applies active rules to requests. This is a useful way to understand a configurable integration service.

A change needs validation and an activation plan. A saved draft is different from the version currently handling requests. Caches and running routes may need a coordinated refresh.

How to reason about it

  1. Prepare and validate the change.
  2. Activate the approved version.
  3. Verify new requests use it and retain a recovery path.
Fictional example

A fictional order mapping is tested before it becomes active.

Remember: A configuration edit can change behavior as much as a code change. Review and versioning still matter.

03ArchitectureController, service, repository, and DTOGive each layer a clear job.+

A controller handles the web boundary. A service coordinates application behavior. A repository handles persistence access. A DTO carries API data; an entity represents stored data.

Mapping DTOs to entities helps separate public contracts from database structures. JPA is a persistence specification; a provider such as EclipseLink implements it.

How to reason about it

  1. Validate and map the request.
  2. Apply application rules in the service.
  3. Use the repository, then map the response.
Fictional example

An update request exposes editable fields while a stored record also has version and audit information.

Remember: Avoid putting every rule in a controller or exposing database entities directly as an API contract.

04CamelRoute, processor, endpoint, and exchangeLearn the pieces before naming patterns.+

A Camel route describes processing from an input to destinations. A processor performs a step. An endpoint connects to a source or destination. An exchange carries a message and processing context.

The body contains the payload; headers contain message metadata. Properties can hold processing context. Keep the purpose and lifetime of each value explicit, especially when replacing the message body.

How to reason about it

  1. Receive a message.
  2. Pass the exchange through focused steps.
  3. Send the output or return a handled outcome.
Fictional example

An order reference is payload, a format hint is metadata, and a correlation ID links operational records.

Remember: Internal context is not automatically an outbound HTTP header. Avoid forwarding internal data unnecessarily.

05CamelPipes and filters: a sequence of stepsBuild a readable processing pipeline.+

A pipeline applies steps in an intended order. Each has a narrow responsibility and an input/output agreement: validate, translate, invoke, or map a result.

A chain of processors supports the pipeline concept. It does not by itself prove a specific Camel DSL operator or a custom GoF Chain of Responsibility implementation.

How to reason about it

  1. Give each step one responsibility.
  2. Document the context it reads and changes.
  3. Define whether failure stops the flow or produces a handled result.
Fictional example

A fictional route validates a reference, creates a provider request, calls a service, and formats the reply.

Remember: Changing the order can change meaning. A successful final step does not prove every earlier step ran.

07CamelDynamic route lifecycleA definition, a running route, and its configuration are different.+

A configurable service can create routes at runtime. Lifecycle operations include creating, registering, starting, stopping, and removing a route.

Replacing a definition needs a plan for in-flight requests. A route can exist but be stopped, and an old route may still be completing work during a change.

08CamelTranslation, templates, and enrichmentChange representation while preserving meaning.+

Transformation can rename fields, reshape nested data, or change formats. Velocity renders templates, JSLT transforms JSON, and XSLT transforms XML. They are different tools.

Enrichment adds information needed later, such as an approved configuration value or an earlier result. Template composition reuses structure, but needs clear missing-value and override rules.

How to reason about it

  1. Define input and output contracts.
  2. Handle types, escaping, missing values, and namespaces.
  3. Validate the produced message.

A fictional provider needs a nested order object while the caller supplies a flat request.

09CamelChaining, branching, and combined resultsUnderstand control flow before assuming parallelism.+

Chaining connects dependent steps. Branching organizes or selects paths. Combining results builds an output from selected earlier results. These can use ordinary application logic or framework features.

A branch diagram does not prove concurrent execution. A merge is not enough to establish Camel Aggregator EIP, which has grouping and completion rules.

How to reason about it

  1. Identify dependencies between steps.
  2. Check whether execution is sequential or concurrent.
  3. Define completion and partial-failure handling.
Fictional example

A fictional overview combines order and shipping information without assuming how calls are scheduled.

Remember: Do not claim Splitter, Aggregator, multicast, or parallel execution just because outputs are combined.

10Design patternsDependency injection and compositionReceive the collaborators a component needs.+

Dependency injection supplies collaborators instead of constructing them repeatedly inside business methods. Spring manages objects and wires their dependencies. Composition builds behavior from cooperating objects.

A narrow interface makes expected behavior clear. Another implementation can replace one concern without changing every caller and can help focused tests.

How to reason about it

  2. Supply an implementation through the container.
  3. Keep configuration and lifecycle ownership clear.

11Design patternsSingleton scope and shared stateOne shared object has a limited scope.+

Spring normally shares one instance per bean definition in one container. A classic Singleton controls creation in the class itself. The ownership and scope differ.

A shared instance may serve many requests concurrently. Keep per-request information out of shared mutable fields. Other processes still have their own instances; lazy creation also needs a safe concurrency design.

How to reason about it

  1. Identify who creates the object and its scope.
  2. Separate stable configuration from request state.
  3. Protect shared mutable state appropriately.
Fictional example

Several fictional requests share a stateless formatter while keeping separate request contexts.

Remember: Singleton does not mean one object across a cluster or guarantee thread safety.

12Design patternsStrategy, registry, and simple factorySelecting behavior and creating an object are different jobs.+

Strategy places alternative behaviors behind a common contract. A registry or resolver chooses an available implementation. A simple factory creates an object and centralizes construction choices.

A class called Factory may only select prebuilt strategies. GoF Factory Method more specifically varies object creation through an overridable creation method. Describe the behavior, not just the class name.

How to reason about it

  1. Identify what varies.
  2. Decide whether selection or construction is needed.
  3. Keep callers dependent on the contract.
Fictional example

A fictional service selects between two SOAP invocation approaches behind one interface.

Remember: A factory does not necessarily create a fresh object for every request. Not every selector is Factory Method.

An adapter converts between interfaces or data models. An SPI defines a contract an extension can implement. These isolate specialized transport or environment behavior.

An extension contract should explain inputs, allowed changes, lifecycle, errors, and compatibility. An interface being available does not prove an implementation is installed and active.

15Design patternsFramework proxies and request contextInterception and data lifetime are separate ideas.+

A proxy stands between a caller and an object. Spring can use proxies to apply concerns such as transactions. A framework interception mechanism is different from a custom application Proxy implementation.

Request context belongs to a particular unit of work. Thread-local storage belongs to a thread, which may be reused by a pool. Context propagation and cleanup therefore need explicit care.

How to reason about it

  1. Identify what intercepts a call and why.
  2. Keep request data within its intended lifetime.
  3. Clean up context and test reused worker threads.

A fictional transactional service call is intercepted by a framework while each request keeps its own context.

Remember: ThreadLocal is not request bean scope, and inherited context does not automatically reach existing pool threads.

16CachingWhat is cached: objects, metadata, tokens, or responses?Name the cached item before discussing performance.+

An object cache reuses an expensive client or serializer. A metadata cache reuses configuration. A token store reuses a still-valid credential. A response cache reuses a business result.

These solve different problems. Reusing a SOAP client may avoid setup while still making a fresh provider call for every request.

How to reason about it

  1. Identify the reusable item.
  2. Measure the work reuse avoids.
  3. Choose a lifecycle suitable for that item.

A fictional SOAP client handles several lookups, but every lookup still reaches the provider.

Remember: A component called a cache does not establish that business responses are cached.

17CachingCache keys, ownership, and safe reuseKeys describe when cached values are interchangeable.+

A key must capture what changes the meaning or safe reuse of an entry. A broad key can mix incompatible contexts; a very narrow key can create many rarely reused entries.

Shared clients should not retain another caller's mutable request or authentication state. Entries may own resources that need cleanup when replaced.

How to reason about it

  1. Define equivalence for cached values.
  2. Keep per-request data safely isolated.
  3. Plan resource cleanup and memory bounds.

A fictional client with one transport configuration cannot always substitute for a differently configured client.

18CachingTTL, eviction, invalidation, and refreshLifetime controls have different meanings.+

TTL limits a specified entry or resource lifetime. Eviction removes entries, often to bound memory. Invalidation removes incorrect or outdated data. Refresh replaces a value.

A scheduled whole-cache clear is not per-entry TTL. A pooled connection's lifetime is not automatically the lifetime of the cached client that uses the pool.

How to reason about it

  1. Identify the resource a setting controls.
  2. Choose how staleness is detected or bounded.
  3. Test misses and reloading after removal.
Fictional example

A fictional mapping changes and needs a refresh policy to make the new value visible.

Remember: Clearing a large cache can trigger many simultaneous reloads. Clearing is not free.

19CachingLocal and distributed cachesKnow where cached data lives.+

A local cache lives in one process. A distributed cache shares data across processes through a networked system such as Coherence. A near cache combines a local front with a backing cache.

Trade-offs include consistency, network cost, serialization, memory, and failure handling. Selecting a local mode is different from automatically failing over to a local cache during a shared-cache outage.

How to reason about it

  1. Identify the owning process or cluster.
  2. Define how updates reach readers.
  3. Specify miss, outage, and invalidation behavior separately.
Fictional example

Two fictional application instances must observe the intended mapping version after an update.

Remember: A JVM-local lock does not coordinate every server. Different cache backends need not have identical policies.

Several requests may discover expiry at once. A refresh guard reduces duplicate work only within its actual coordination scope.

22ReliabilityStructure, configuration, and business validationValidation happens at different boundaries.+

Structural validation checks the shape of data. Configuration validation checks consistency, references, and allowed flows. Business validation checks whether values meet domain rules.

Fail-fast checking stops after an error; collect-all checking reports several errors together. The right choice depends on cost, dependencies between checks, and the caller's needs.

How to reason about it

  2. Validate a configuration before activation.
  3. Check provider results before mapping them into a caller's response.

A transport failure, malformed reply, business rejection, and transformation failure are different outcomes. Classification should happen where the failure is understood.

A consistent response model helps callers choose whether to correct, wait, or escalate. Safe diagnostics retain correlation and step context while avoiding private payloads and exposed stack traces.

24ReliabilityTimeouts, retries, and idempotencyRepeated work can create repeated effects.+

A timeout bounds waiting. A retry starts another attempt. Idempotency prevents repeated handling of the same intended operation from creating duplicate effects.

A timeout can be ambiguous: the remote work may have succeeded while its reply was lost. Backoff and retry limits reduce load but do not solve that correctness problem.

How to reason about it

  1. Decide which failures can be retried.
  2. Check safety or duplicate prevention.
  3. Bound attempts and define recovery for uncertain outcomes.
Fictional example

A fictional status lookup is often safer to repeat than a request creating a new order.

Remember: HTTP-client retries, route redelivery, and application retries can have different scopes and defaults.

05 / Explore caching

Same request. Different cache state.

This fictional cache stores service-mapping metadata, not order results. Choose a state and follow the difference.

Reuse a current mapping

  1. Look up a fictional service mapping by its complete key.
  2. Find an entry that is reusable under the chosen policy.
  3. Use it and continue; the provider call still runs when needed.

The lesson: A metadata cache hit saves a lookup. It does not mean the business response came from the cache.

Load, then reuse

  1. Find no usable entry for the key.
  2. Load the approved mapping from its source.
  3. Store a suitable reusable value and continue.

The lesson: Several callers can miss together. A loading guard may reduce duplicate work, but its coordination scope matters.

Remove stale assumptions

  1. An approved mapping is changed in the example.
  2. Invalidate or refresh the affected entries using a documented policy.
  3. Check that relevant application instances observe the new version.

The lesson: Clearing one local map does not automatically clear other JVMs. A JVM is a running Java process.

06 / Make it stick

A practical reading path

1. Explain the boundary

Describe consumer, provider, contract, route, and transformation using the fictional order lookup.

2. Follow one request

Identify the input, output, failure, and useful operational signal at each step.

3. Name patterns precisely

Ask what varies. Selecting an existing implementation is a resolver; creating an object is a factory responsibility.

4. Describe one cache completely

Name the cached item, key, owner, lifetime, invalidation, memory bound, concurrency, and failure behavior.

5. Check assumptions

Separate a library capability from enabled behavior, a local lock from a distributed lock, and a branch from parallel execution.

6. Connect to my experience

Use general examples for mechanisms and resume-backed statements for personal contributions and outcomes.

Questions worth revisiting

Is a Spring singleton one object in the entire system?

No. It normally means one object per bean definition per Spring container. Other containers or processes have their own objects. Shared mutable fields still need a concurrency design.

Does caching always make an API faster?

No. Low reuse, poor keys, stale values, synchronization, large entries, and repeated misses can offset the benefit. Measure the part of the request that changed.

Are branches always parallel, and is every merge Camel Aggregator?

No. Branches can run sequentially. Combining outputs can be ordinary application logic. Camel Aggregator is a specific EIP with grouping and completion rules.

Does a circuit breaker guarantee safe retries?

No. A breaker controls whether calls are allowed according to its mode and policy. A retry repeats work. Duplicate prevention and recovery need their own design.

Does finding a feature in source prove I built or deployed it?

No. Source can show supported capabilities. Personal ownership and production enablement require separate evidence.
